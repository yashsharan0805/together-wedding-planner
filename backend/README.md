# LibreWeddingPlanner

This is the upstream reference README. For Together setup, use [the root README](../README.md); the upstream Compose/seed instructions below are not the Together setup.

LibreWeddingPlanner is Free, Open Source Software that helps organize several aspects of a wedding.

## Features

Explore all features in the [project documentation](https://libreweddingplanner.org/docs/dashboard).


# Development setup

LibreWeddingPlanner is made of two main pieces:

- The backend (this repo), built with Ruby (on Rails)
- The frontend (repo [here](https://codeberg.org/LibreWeddingPlanner/libre-wedding-planner-frontend)), built with NextJS and React. You will need both to have the service fully working.
- The engine, which takes care of calculating a good distribution of guests in tables and buses.

Both repositories are expected to live have a common parent directory:

```
projects <or anything else>
  |-> libre-wedding-planner-backend
  |-> libre-wedding-planner-frontend
  |-> libre-wedding-planner-engine
```

## Docker compose

Docker compose is the recommended way to run LibreWeddingPlanner for development purposes. After downloading both repositories, `cd` to the root of `libre-wedding-planner-backend` and run:

```bash
docker compose up --build
```

Several containers will be started:

- backend: starts a Rails server that will act as an API.
- workers: starts a runner of [solid queue](https://github.com/rails/solid_queue/) that takes .care of async tasks.
- frontend: starts a NextJS application in charge of the frontend.
- nginx: A reverse proxy that the backend and frontend under the same domain, and routes all requests to the upstream services.
- db: A Postgres instance used by the backend service.
- glitchtip: An error collector UI
- librecaptcha: A captcha provider
- valkey: A key-value database

The backend service will seed the database with fake data. It's worth noting that the Postgres container does not have a volume, so the application will be seeded every time the container is created.

The backend, frontend and workers have hot-reloading enabled, so changes made to the codebase should be reflected in the application on the next request.

Please, include this in your `/etc/hosts` file:

```
127.0.0.1 libre-wedding-planner.app.localhost
```

Once all containers have started, visit http://libre-wedding-planner.app.localhost/default/dashboard to load the application.

## Multitenancy

LibreWeddingPlanner is designed to manage multiple weddings in a single host. All URLs (in the API and the frontend) are scoped under a slug that is unique per wedding. The slug is made of lowercase letters, numbers, and dashes (-).

The development environment is seeded with a wedding whose slug is `default`.

## Error tracking

An instance of [GlitchTip](https://glitchtip.com) is instantiated in http://glitchtip.libre-wedding-planner.app.localhost. In order to make it workfor the first time, visit the URL, create an account, an organization, and Rails project, and a team. Then, locate the DSN configuration in GlitchTip's UI:

```ruby
Sentry.init do |config|
  config.dsn = "http://8c9e55bc8e0c413a8f54a3cfcb4a1721@glitchtip.libre-wedding-planner.app.localhost/1"
  config.traces_sample_rate = 0.01 # 1% of transactions
  config.breadcrumbs_logger = [:active_support_logger, :http_logger]
end
```

Finally, export the following environment variable in your console initialization script (e.g., `~/.zshrc`), replacing the host by `glitchtip:8000` (to ensure requests are sent using docker's network):

```bash
export SENTRY_BACKEND_DSN="http://8c9e55bc8e0c413a8f54a3cfcb4a1721@glitchtip:8000/1"
```


## Email delivery

In the development environment, real emails will not be sent. You can visit http://libre-wedding-planner.app.localhost/letter_opener/ to get a list of emails generated by the application.

## Testing

Unit tests can be executed with

```
bundle exec rspec
```

## API documentation

Generate the OpenAPI documentation with the command:

```
rake rswag:specs:swaggerize
```

The documentation is available in Swagger UI in http://libre-wedding-planner.app.localhost/api/api-docs/index.html. If testing the API through the UI, you will need to select the second server (which includes the `/api` path), intended for development.

## Dependency matrix

The CI of this project is configured to run against the latest stable Ruby version (required) and any preview of the next version. This should help us detect upstream errors and required dependency updates.

The CI runs against the last and second-to-last versions of Postgres. Although Postgres versions have 5-year support, we cannot afford to run the CI against 5 different versions at the moment. Versions of Postgres other than the last one only run against the latest stable ruby.
